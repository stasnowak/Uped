# Uped deployment research (Alpine LXC on Proxmox, curl|sh installer, CI) — 2026-10-07

Sandbox note: alpinelinux.org, pve.proxmox.com, docs.docker.com, MDN, docs.github.com and download.proxmox.com were blocked by the egress proxy. Facts below come from GitHub-hosted primary sources (OpenRC man pages, pve-docs mirror, mdn/content, community-scripts, k3s/tailscale installers, action release pages) plus web-search summaries. Anything not primary-sourced is marked **(unverified)**.

## 1. Alpine + OpenRC service

**Versions.** Alpine 3.22 released 2025-05-30 (support to 2027-05-01); 3.23 released 2025-12-04 (support to 2027-11-01); 3.24.0 released ~May/June 2026 with Go 1.26, kernel 6.18 LTS **(exact date unverified)**. Current point releases as of early Oct 2026 appear to be 3.22.6 / 3.23.6 / 3.24.2 **(unverified, from news headline)**. `apk add go` gives Go 1.25.x on 3.23 (go-1.25.5-r0 at release, later 1.25.9-r0; 153 MiB installed per pkgs.alpinelinux.org), 1.26 on 3.24, 1.24 on 3.22 **(3.22 unverified)**. Proxmox's `pveam` catalogue usually lags Alpine by one release; community-scripts' `ct/alpine.sh` defaults to `var_version=3.24` (as of Oct 2026), which implies an `alpine-3.24-default` template now exists in the catalogue, but check with `pveam update && pveam available --section system | grep alpine` **(catalogue contents unverified)**. Target 3.22+ and avoid anything that needs a specific point release.

**Facts that shape the installer** (busybox userland): `/bin/sh` is busybox ash (no bash in the base template) → install.sh must be POSIX sh. `curl` is NOT in the base template; busybox `wget` with `ssl_client` + `ca-certificates-bundle` is, so `wget -qO- URL | sh` works out of the box (document both; tell users `apk add curl` if they want the curl one-liner) **(ssl_client-in-template: high confidence, unverified here)**. busybox has `sha256sum -c`, `install`, `mktemp -d`, `adduser/addgroup`, and `ip route get` (verified in busybox `networking/libiproute/iproute.c`: `CMD_get` → `iproute_get`, bare address accepted).

**User / dirs:** `addgroup -S uped 2>/dev/null; adduser -S -D -H -h /var/lib/uped -s /sbin/nologin -G uped uped 2>/dev/null` (busybox flags: `-S` system, `-D` no password, `-H` no home dir creation). Data `/var/lib/uped` (0750 uped:uped), logs `/var/log/uped`, config `/etc/conf.d/uped`.

**Init script** (`/etc/init.d/uped`, chmod 755). Variables per `openrc-run(8)` and `supervise-daemon(8)` (OpenRC master, github.com/OpenRC/openrc/man/): `command_user` changes uid[:gid]; `output_log`/`error_log` redirect stdout/stderr to files; `directory` = chdir; `pidfile` is the *supervisor's* pidfile; `respawn_delay` (default 0), `respawn_max` (default 10, 0 = unlimited), `respawn_period` (default 12s); `umask`; `capabilities`. The daemon must stay in the foreground (no self-daemonising).

```sh
#!/sbin/openrc-run
# /etc/init.d/uped — generated by install.sh
name="uped"
description="Uped LAN file drop"
supervisor=supervise-daemon
command="/usr/local/bin/uped"
# conf.d vars are plain shell vars (not exported) — pass them as flags:
command_args="--listen ${UPED_LISTEN:-:8080} --data ${UPED_DATA_DIR:-/var/lib/uped} ${UPED_EXTRA_ARGS:-}"
command_user="uped:uped"
directory="/var/lib/uped"
pidfile="/run/uped.pid"
output_log="/var/log/uped/uped.log"
error_log="/var/log/uped/uped.log"
respawn_delay=5
respawn_max=0
umask=027

depend() {
    need net
    after firewall
    use dns logger
}

start_pre() {
    checkpath -d -m 0750 -o uped:uped "${UPED_DATA_DIR:-/var/lib/uped}"
    checkpath -d -m 0750 -o uped:uped /var/log/uped
}
```

`/etc/conf.d/uped`: `UPED_LISTEN=":8080"`, `UPED_DATA_DIR="/var/lib/uped"`, `UPED_EXTRA_ARGS=""`. (If the binary reads env vars instead of flags, write `export VAR=...` lines in conf.d.) Enable: `rc-update add uped default && rc-service uped start`. Alpine's wiki prefers `supervisor=` in conf.d rather than the script, but k3s's installer hard-codes it in the init script (verified in k3s install.sh) and that is fine for a third-party installer. Wiki: https://wiki.alpinelinux.org/wiki/Writing_Init_Scripts (blocked here). k3s's generated OpenRC unit (`supervisor=supervise-daemon`, `output_log`/`error_log`, `respawn_delay=5`, `respawn_max=0`, `depend(){ after network-online; want cgroups; }`) is a good real-world reference: https://github.com/k3s-io/k3s/blob/master/install.sh

## 2. Proxmox community-scripts pattern (brief)

- `ct/<app>.sh` runs on the PVE host: it sources `core/build.func` from **github.com/community-scripts/core** (engine was split out of ProxmoxVE in 2026), sets `APP`, `var_cpu/var_ram/var_disk/var_os/var_version/var_unprivileged`, defines `update_script()`, then calls `start; build_container; description`. Alpine defaults in `ct/alpine.sh`: 1 vCPU, 512 MB, 1 GB disk, unprivileged=1, arm64 allowed.
- `build_container` creates the LXC (pveam template download, `pct create`), then runs `install/<app>-install.sh` inside it via `lxc-attach`; that file begins `source /dev/stdin <<<"$FUNCTIONS_FILE_PATH"` and calls `color; verb_ip6; catch_errors; setting_up_container; network_check; update_os; ... apk add ...; motd_ssh; customize; cleanup_lxc` (Alpine flavour = `alpine-install.func`/`alpine-tools.func`).
- Third-party reuse: build.func resolves script paths (`ct/…`, `install/…`) against `COMMUNITY_SCRIPTS_URL` (default `raw.githubusercontent.com/community-scripts/ProxmoxVE/main`) and the engine against `COMMUNITY_SCRIPTS_CORE_URL`; the header says "a fork/branch of the scripts resolve separately". So a `stasnowak/Uped` repo with `ct/uped.sh` + `install/uped-install.sh` can run with `COMMUNITY_SCRIPTS_URL=https://raw.githubusercontent.com/stasnowak/Uped/main` exported first — plausible but **end-to-end unverified**, and the engine changes often (it was refactored in 2026). Treat it as an optional nicety; the primary path stays "create an Alpine LXC, then `curl|sh` inside".
- Resources for a Go file server: 1 vCPU, 256–512 MB RAM, 1–2 GB rootfs is plenty (binary ~10–15 MB; Go streams uploads to disk if you use `r.MultipartReader()` rather than `ParseMultipartForm`); put data on a separate mount point (section 6). Unprivileged LXC (PVE default) is fine; no special features needed.

## 3. `curl | sh` installer

Reference implementations (both verified by reading the source): **k3s** `install.sh` (arch map, sha256 verification from a per-arch checksum file, `mktemp -d` → `chmod 755` → `mv -f` into `/usr/local/bin`, OpenRC+systemd unit generation, generated `*-uninstall.sh`, "no change detected so skipping service restart" via before/after hash compare) and **tailscale** `scripts/installer.sh` (`set -eu`, everything inside `main()` called on the last line so a truncated download cannot execute half a script, `/etc/os-release` detection, `$CURL` abstraction over curl/wget, root/sudo/doas detection, Alpine branch does `apk add` + `rc-update add` + `rc-service start`). https://github.com/tailscale/tailscale/blob/main/scripts/installer.sh . Flagsmith's POSIX `install.sh` is a smaller checksums.txt example.

Structure for `install.sh` (POSIX sh, `set -eu`, `main "$@"` last):
1. Must be root (LXC console is root; else `doas`/`sudo`). Refuse non-Alpine/non-OpenRC with a clear message (check `/etc/alpine-release`, `command -v rc-service`).
2. Arch: `case "$(uname -m)" in x86_64|amd64) arch=amd64;; aarch64|arm64) arch=arm64;; *) fatal;; esac`.
3. Fetch: `dl() { if command -v curl >/dev/null; then curl -fsSL "$1" -o "$2"; else wget -qO "$2" "$1"; fi; }`.
4. Latest release without API/jq: `https://github.com/stasnowak/Uped/releases/latest/download/uped_linux_${arch}.tar.gz` and `.../releases/latest/download/checksums.txt`. GitHub resolves `latest` = newest non-draft, non-prerelease release sorted by `created_at` (docs: "Linking to releases" / REST `releases/latest`). The `api.github.com/.../releases/latest` route needs JSON parsing and is rate-limited (60/h unauthenticated) — avoid. To display the version: `curl -sIL -o /dev/null -w '%{url_effective}' https://github.com/stasnowak/Uped/releases/latest` → `.../tag/vX.Y.Z` (k3s uses the same `%{url_effective}` trick); busybox wget lacks this, so also embed the version in the binary (`uped --version`). Support `UPED_VERSION=vX.Y.Z` override → `releases/download/<tag>/...`.
5. Verify: `cd "$tmp" && grep " uped_linux_${arch}.tar.gz$" checksums.txt | sha256sum -c -` (busybox OK).
6. Atomic replace: extract to `$tmp`, `chmod 755`, `mv -f "$tmp/uped" /usr/local/bin/uped` (rename on same fs is atomic; a running process keeps the old inode).
7. Idempotent upgrade: if `/usr/local/bin/uped` exists and hash equals the new one, say "already up to date" and skip restart; otherwise `rc-service uped stop` (ignore failure), replace, (re)write `/etc/init.d/uped` (always, so fixes propagate), never overwrite an existing `/etc/conf.d/uped`, `rc-update add uped default` (idempotent), `rc-service uped start`.
8. `--uninstall`: `rc-service uped stop; rc-update del uped default; rm -f /etc/init.d/uped /usr/local/bin/uped`; keep `/etc/conf.d/uped` and `/var/lib/uped` unless `--purge` (then also `deluser uped`). Since `curl … | sh` cannot take flags easily, document `curl -fsSL … | sh -s -- --uninstall` and also install the script as `/usr/local/bin/uped-uninstall` (k3s pattern).
9. Final banner: `ip=$(ip -4 route get 1 2>/dev/null | awk '{for(i=1;i<=NF;i++) if($i=="src"){print $(i+1); exit}}')`; fallback `hostname -i | awk '{print $1}'` (busybox `hostname -i` resolves the hostname via /etc/hosts, which Proxmox manages: it is reliable for static-IP containers, often 127.0.1.1 for DHCP ones **(unverified)**). Print `http://$ip:8080/`.

**If there are no GitHub Releases yet:** (a) build from source on the LXC: `apk add go git` ≈ 160 MB + module/build cache; a small net/http + embed.FS app builds in roughly 1–3 min on 1 vCPU and needs ~1 GB free disk and ≥512 MB RAM **(timing is an estimate)**; too heavy for the default 1 GB-disk Alpine LXC. (b) a rolling `latest`/`nightly` release re-created by CI on every push (softprops `tag_name: nightly` + `prerelease: true`) — but `releases/latest/download` ignores prereleases, and a moving tag confuses `go install …@latest` and checksums. **Recommendation:** make real tagged releases from CI (`git tag v0.1.0 && git push --tags` is the whole cost); keep a `--from-source` installer flag and `go install github.com/stasnowak/Uped@latest` as documented fallbacks only.

## 4. GitHub Actions outline

Versions are the latest tags on each action's GitHub releases page as of 2026-10-07: `actions/checkout@v7` (v7.0.1), `actions/setup-go@v7` (v7.0.0), `softprops/action-gh-release@v3` (v2 is EOL per README), `docker/login-action@v4` (v4.6.0), `docker/setup-qemu-action@v4` (v4.4.0), `docker/setup-buildx-action@v4` (v4.4.1), `docker/metadata-action@v6` (v6.2.0), `docker/build-push-action@v7` (v7.4.0), `goreleaser/goreleaser-action@v7` (v7.2.3). (Docker's own README examples use login@v4 / qemu@v4 / buildx@v4 / build-push@v7.)

- **ci.yml** (push/PR): checkout → setup-go (`go-version-file: go.mod`, cache on) → `go vet ./...` → `go test -race ./...` → matrix `GOOS=linux GOARCH={amd64,arm64} CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" ./...` (optionally `golangci-lint-action`).
- **release.yml** (`on: push: tags: ['v*']`, `permissions: {contents: write, packages: write}`):
  1. Build both arches with `-ldflags "-s -w -X main.version=${GITHUB_REF_NAME}"`, tar each as `uped_linux_<arch>.tar.gz`, `sha256sum *.tar.gz > checksums.txt`, then `softprops/action-gh-release@v3` with `files: |` (globs), `generate_release_notes: true`, `fail_on_unmatched_files: true`. Or `goreleaser/goreleaser-action@v7` with a `.goreleaser.yaml` — if so set `checksum: {name_template: checksums.txt}` (the default name is version-specific and breaks the `latest/download/checksums.txt` URL).
  2. Image: `docker/login-action@v4` (registry `ghcr.io`, `username: ${{ github.actor }}`, `password: ${{ secrets.GITHUB_TOKEN }}`) → `docker/metadata-action@v6` (`images: ghcr.io/${{ github.repository }}`, tags `type=semver,pattern={{version}}`, `type=semver,pattern={{major}}.{{minor}}`, `latest`) → `docker/setup-buildx-action@v4` → `docker/build-push-action@v7` with `platforms: linux/amd64,linux/arm64`, `push: true`, `tags/labels` from metadata, `cache-from/to: type=gha`. Dockerfile: `FROM --platform=$BUILDPLATFORM golang:1.25-alpine AS build` + `ARG TARGETOS TARGETARCH` + `CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH go build …`, then `FROM scratch` (or `gcr.io/distroless/static:nonroot`), `COPY --from=build /out/uped /uped`, `USER 65532:65532`, `VOLUME /data`, `EXPOSE 8080`. Cross-compiling in Go this way means `setup-qemu-action` is unnecessary (only needed for native-arch `RUN` steps). Packages on ghcr.io inherit repo visibility once linked; the token's `packages: write` is enough for first push.

## 5. Plain-HTTP LAN origin

Secure contexts (MDN `Web/Security/Defenses/Secure_Contexts`, mdn/content source): only `https://`, `wss://`, `http://localhost`, `*.localhost`, `127.0.0.0/8`, `::1`, `file://`. **`http://192.168.x.y` is not a secure context**, so (per MDN's "features restricted to secure contexts" list) these are unavailable: Service Workers (no PWA install/offline), Async Clipboard API (`navigator.clipboard` is undefined; the `document.execCommand('copy')` + temporary textarea fallback still works in all browsers), Web Share / Share Target, `getUserMedia`, Notifications/Push, File System Access API (`showSaveFilePicker`), Web Crypto `crypto.subtle` (and `crypto.randomUUID()` — generate IDs server-side), Storage API `persist()`, Web Locks, WebCodecs, Geolocation, WebAuthn, `Cache-Control: immutable`. Not restricted and fine over http: `<input type=file multiple>` (including mobile `capture`), HTML5 drag-and-drop/`DataTransfer`, `XMLHttpRequest` with `upload.onprogress` (use XHR, not `fetch`, for upload progress — fetch upload streams need HTTP/2 over TLS), `fetch` for everything else, `EventSource`/SSE, WebSocket `ws://`, `<a download>`, Range requests/resumable downloads (server-side), `localStorage`, Web Workers, `sendBeacon`. Browser chrome shows "Not secure"; Chrome 154 (Oct 2026) enables "Always Use Secure Connections" by default but **explicitly exempts private IPs, single-label hostnames and intranet names**, so plain-HTTP LAN apps keep working without a warning (heise, cyberinsider coverage of Google's Oct-2025 announcement).

**mDNS/.local:** Avahi inside an *unprivileged* LXC hits a well-known problem: `avahi-daemon.conf` sets `rlimit-nproc=2`; rlimits bind to the host kernel uid, which all unprivileged containers share (100000+N), so the chroot helper `fork()` fails ("Resource temporarily unavailable") as soon as the host or another container runs anything as that uid (lxc/lxc#404, canonical/lxd#2948). Fix is `--no-rlimits` / commenting the `[rlimits]` section; on Alpine `apk add avahi && rc-update add avahi-daemon && rc-service avahi-daemon start` (whether Alpine's shipped conf enables rlimits: **unverified**). Multicast over the veth/vmbr0 bridge works. Clients: macOS/iOS/Windows/most Linux resolve `.local`; Android/Chrome-on-Android generally do not **(commonly reported, unverified)**. Pragmatic answer: DHCP reservation (or static IP in the PVE network tab) + print the URL at install and in `uped --status`; many home routers also resolve the DHCP hostname (`http://uped/`, `uped.lan`, `uped.fritz.box`), and Proxmox sends the CT hostname in DHCP requests. Offer avahi as an opt-in flag, not the default.

## 6. Unprivileged LXC storage for the upload dir

- pve-docs (`pct.adoc`, github.com/proxmox/pve-docs): "The root UID 0 inside the container is mapped to an unprivileged user outside the container"; the default map is container uid N → host uid 100000+N (so the `uped` user, e.g. uid 100, is host uid 100100; check with `id uped` inside). "With unprivileged containers you might run into permission problems caused by the user mapping and cannot use ACLs." Bind mounts: `pct set <CTID> -mp0 /mnt/bindmounts/uped,mp=/var/lib/uped` (or `mp0: /mnt/bindmounts/uped,mp=/var/lib/uped` in `/etc/pve/lxc/<CTID>.conf`); source must contain no symlinks; "The contents of bind mount points are not backed up when using `vzdump`"; only reserved dirs under e.g. `/mnt/bindmounts`, never system dirs. Then on the host `chown -R 100100:100100 /mnt/bindmounts/uped` (substitute the mapped uid) — or map a host group via `lxc.idmap` + `/etc/subuid|subgid` (Proxmox forum tutorial "Unprivileged LXCs - Mount CIFS shares", thread 101795) when the host must also own the files.
- Simplest for a home user (recommended): either grow the rootfs (`pct resize <CTID> rootfs +20G`, online, **syntax from memory**) or add a storage-backed mount point `pct set <CTID> -mp0 local-lvm:50,mp=/var/lib/uped` ("`STORAGE_ID:SIZE_IN_GB` … will automatically allocate a volume"); it is managed by PVE (snapshots, `pct move-volume`, resize) and included in vzdump when `backup=1` is on the mp line. No uid gymnastics: the volume is formatted fresh and the container's own `chown` applies.
- Installer implication: `/var/lib/uped` may already be a mount point; only `chown` the top directory (no `-R` over gigabytes), warn and continue if it is not writable by `uped`, and let `UPED_DATA_DIR` in conf.d point elsewhere.
